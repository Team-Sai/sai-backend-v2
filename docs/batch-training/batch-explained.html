01 / WHY

왜 배치가 필요한가

사용자가 화면을 열지 않아도, 시간이 지나면 해야 할 일이 생깁니다.

새 거래가 들어왔다은행 내역을 가져와 상환·정산에 반영
납부일이 다가왔다D-3 · D-1 · 당일에 사용자 알림 생성
기한이 지났다연체를 표시하고 장기 미납을 정리
사용자 요청계약·정산을 생성한다
→
업무 DB기한·상태·계좌를 보관한다
→
정기 배치대상을 찾아 시간에 따른 후속 처리를 한다

배치는 정해진 범위의 데이터를 반복 처리하는 작업입니다. 스케줄은 실행 시점을 정하고, Spring Batch는 실행 단위·이력·처리 정책을 제공합니다. 현재 프로젝트는 @Scheduled로 자정 실행을 예약하고, Chunk Step에 계좌별 반복 처리를 설정합니다.

이 프로젝트에서의 가치

기한 처리를 사용자 접속에 의존하지 않고, 계좌별 동기화와 실패 재처리를 일정한 정책으로 수행합니다. 재기동 후 정기정산 생성은 누락 회차를 따라잡고, 리마인드는 실행 기준일의 D-3·D-1·당일 대상만 조회합니다.

02 / CONCEPTS

Job · Step · 실행 이력

Job은 업무 하나의 이름이고, Step은 그 업무를 수행하는 처리 단계입니다.

Job · transactionSyncJob은행거래 동기화라는 업무
↓ 이 프로젝트는 10개 Job 모두 Step 1개
Step · transactionSyncStepReader / Processor / Writer와 처리 정책
↓ 실제 로직 위임
도메인 서비스동기화 · 매칭 · 저장 · 상태 변경
용어쉽게 설명하면현재 코드에서
Job실행할 업무의 설계도은행거래 동기화, 정산 연체 등 10개
StepJob 안의 처리 단계현재 각 Job에 1개씩 연결
JobInstanceJob 이름과 식별 파라미터로 구분하는 논리적 작업baseDate와 매번 바뀌는 runId를 전달
JobExecution / StepExecution실제로 실행한 이력과 결과상태, 시작·종료 시각, read/write/skip 집계
JobParameters이번 실행에 넣는 입력값baseDate: 업무 기준일 / runId: 실행 구분
JobRepository배치 실행 기록을 저장하는 곳JDBC 기반 저장소. 업무 데이터 저장소와 역할이 다름

현재는 왜 Step을 하나씩 연결했을까?

각 JobConfig는 .start(해당 Step) 뒤에 .build()를 호출합니다. 거래 Job의 Step은 계좌 조회·동기화·매칭을 하나의 반복으로 묶고, Tasklet Job의 Step은 업무 서비스 한 절차를 호출합니다. 현재 코드의 실행 상태와 집계 경계가 이 한 단계에 모입니다.

JobtransactionSyncJob
→
Step 1개transactionSyncStep
→
Step 내부 반복계좌 조회 → 동기화·매칭 → 로그

여러 Step은 언제 사용하는가?

독립적인 입력·출력, 단계별 실행 결과, 실패 후 재시작 경계가 필요한 업무라면 하나의 Job 안에 여러 Step을 연결할 수 있습니다. 예를 들어 파일 검증 → 데이터 적재 → 결과 보고를 단계별로 나누면 실패한 단계를 실행 이력에서 구분하기 쉽습니다. 재시작 시 실행 여부는 Step 설정과 이전 실행 상태로 결정합니다.

Job파일 처리 · 설계 예시
→
검증 Step파일 형식·필수값 검사
→
적재 Step유효 데이터 저장

다중 Step 그림은 설계 개념을 설명하는 예시입니다. 현재 프로젝트의 각 Job은 단일 Step으로 구성되어 있습니다.

04 / PROCESSING

Chunk와 Tasklet의 차이

선택 기준은 데이터 처리 단위, 반복 주체, 실패 제어 방식입니다.

Chunk · 항목 중심 반복

Reader계좌 1개씩 읽기
→
Processor계좌별 업무 수행
→
Writer최대 50개 결과 전달

프레임워크가 읽기·처리·쓰기 반복과 chunk 경계를 관리합니다. 이 프로젝트는 계좌 50개로 설정합니다. chunk(50)은 Writer에 전달할 계좌 DTO 묶음의 크기와 Step의 처리 경계를 정합니다.

Tasklet · 업무 절차 호출

Tasklet기준일 해석
→
Service조회·반복·상태 갱신
→
FINISHEDStep 종료

개발자가 서비스 내부의 반복·페이징·예외 집계를 구성합니다. 한 번 호출해 수천 건을 처리할 수도 있습니다. Tasklet도 CONTINUABLE을 반환해 반복할 수 있지만, 현재 8개는 FINISHED로 끝납니다.

비교Chunk현재 Tasklet
반복 주체Spring Batch의 항목 처리 루프업무 서비스의 반복문·벌크 쿼리
오류 정책Step의 retry / skip 설정서비스별 catch·집계·임계값

10개 Job은 왜 이 방식을 쓰는가

방식은 코드에서 확인한 사실입니다. 아래 선택 이유는 구현 구조에 근거한 해석이며, 개발 당시 의사결정을 단정하지 않습니다.

Job방식이 구조에 맞는 이유
transactionSyncJobChunk 50AVAILABLE 계좌마다 동일한 동기화·매칭을 수행하고 특정 은행 조회 예외를 재시도·스킵하기 적합
bankTransactionRetryJobChunk 50동일 계좌 Reader를 재사용하고 계좌별 재매칭 실패를 격리하기 적합
recurringSettlementGenerationJobTasklet정기설정 → 누락 회차 반복 → 회차별 생성이라는 중첩 절차를 서비스가 관리
repaymentScheduleOverdueJobTasklet조건에 맞는 스케줄을 벌크 UPDATE 한 번으로 갱신
settlementOverdueJobTasklet정산별 기준일 판정 후 참여자 결제의무를 정산 단위 트랜잭션으로 변경
repaymentDueReminderJobTaskletD-3·D-1·당일 조회, 채무자 확인, 개별 알림·실패 임계값을 한 절차로 관리
settlementDueReminderJobTasklet정산 → 참여자 → 최신 미납 의무를 탐색해 알림을 생성하는 다단계 절차
settlementAbandonmentJobTasklet감지·중복 기록·미전송 Slack 재전송이라는 두 단계 절차
settlementWriteOffJobTasklet상각 후보 조회·상각·관련 정산 자동종결을 연결
repaymentWriteOffJobTasklet후보 ID 조회 후 조건부 벌크 UPDATE를 수행
Tasklet은 서비스의 업무 절차를 실행합니다

오히려 복합 업무 절차를 기존 서비스에 위임할 때 간결합니다. 데이터가 커져 대상별 체크포인트·재시작 제어가 필요해지면 일부 Tasklet을 Chunk로 바꾸는 선택도 가능합니다.
